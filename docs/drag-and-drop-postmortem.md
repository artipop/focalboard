# Постмортем: перетаскивание карточек, которое переставало работать

**Когда:** июль–август 2026, во время миграции webapp с react-dnd на `@dnd-kit/react`.
**Симптом:** несколько перетаскиваний проходят, потом доска перестаёт реагировать на
нажатия — молча, без ошибок в консоли. Иногда не работает с самого первого нажатия,
иногда «отпускает» само по себе через некоторое время.
**Итог:** четыре независимых дефекта. Три в webapp, один — в подключении к базе,
существовавший задолго до миграции и не связанный с перетаскиванием вообще.

## Почему это заняло так много времени

Симптом был один, а причин — четыре, и каждая маскировала остальные. Хуже того,
все четыре давали **одну и ту же наблюдаемую картину**: `pointerdown` в логе и
больше ничего.

Первые пять попыток чинились «по описанию»: гипотеза → правка → просьба
попробовать руками → «всё ещё не работает». Каждый круг занимал час и не давал
знания. Перелом наступил, когда появилось воспроизведение, работающее без
человека — `webapp/cypress/e2e/kanbanDrag.ts`, тридцать перетаскиваний туда и
обратно с проверкой каждого. Десять секунд на прогон. **Три из четырёх дефектов
были найдены в течение часа после того, как он появился.**

Отдельная ошибка ведения: при отладке клиентского симптома серверные логи
отфильтровывались из вывода как шум. Строка `database table is locked: blocks`
лежала в этом выводе несколько часов.

## Дефект 1. Нативный `draggable` на карточке

**Главный.** `kanbanCard.tsx` и `kanbanColumnHeader.tsx` ставили HTML-атрибут
`draggable={!props.readonly}` — наследство react-dnd с его HTML5-бэкендом.

dnd-kit работает на pointer-событиях и, обнаружив нативно перетаскиваемый элемент,
**сознательно уступает браузеру**:

```js
const isNativeDraggable = isHTMLElement(target) && target.draggable &&
    target.getAttribute('draggable') === 'true'
{type: 'dragstart', listener: isNativeDraggable ? this.handleCancel : preventDefault}
```

Браузер начинал нативный драг, который в приложении никто не обрабатывает, слал
`pointercancel`, и dnd-kit отменял перетаскивание, которое ещё не началось. В логе
— `pointerdown` и тишина, даже без `pointerup`.

Кто выиграет гонку — порог нативного драга или пять пикселей сенсора — зависит от
скорости движения руки. Отсюда вся кажущаяся случайность.

**Почему не ловилось e2e:** `cypress-real-events` двигает указатель ровными мелкими
шагами, и сенсор всегда выигрывал. Живая рука так не умеет. Это стоит помнить:
воспроизведение может быть систематически «добрее» человека.

Найдено диагностикой, которая печатала состояние менеджера на отказавшем нажатии —
и назвала причину тем, что **исключила** всё остальное: draggable зарегистрирован,
включён, держит именно нажатую карточку, операция в покое.

Сторож: тест `kanbanCard.test.tsx` падает, если атрибут вернётся.

## Дефект 2. `OptimisticSortingPlugin` ронял React

Плагин из набора по умолчанию у каждого sortable переставляет карточки в DOM сам,
пока идёт перетаскивание. Дальше два владельца одного узла: dnd-kit перенёс
карточку в другую колонку, React считает её там, куда положил сам, и следующий
рендер, удаляющий карточку, зовёт `removeChild` у родителя, который её не держит.

```
NotFoundError: Failed to execute 'removeChild' on 'Node'
  at commitDeletionEffectsOnFiber
```

React падает внутри фазы коммита, дерево рендера после этого сломано — доска
мертва целиком и необратимо.

Виновник найден обёртыванием всех методов DOM, способных переставить узел, с
запоминанием стека последнего перемещения каждой карточки.

**Тонкость:** голый конструктор плагина регистрируется **на менеджере**, а не на
элементе. Отключение его только на карточках ничего не давало — плагин приносили
sortable'ы боковой панели. Исключать нужно у **всех** `useSortable` в приложении.

Цена: пропала живая пересортировка (карточки под курсором больше не расступаются).
Подсветка целевой колонки осталась.

## Дефект 3. Старт перетаскивания ждал низкоприоритетный рендер React

`DragDropProvider` заворачивает `onBeforeDragStart`, `onDragOver`, `onDragMove` и
`onDragEnd` в `trackRendering()`, который кладёт в `renderer.rendering` **ждущий**
промис и резолвит его только когда закоммитится `startTransition`. А менеджер
ровно в этот момент делает:

```js
dragOperation.status.set('initializing')
this.manager.renderer.rendering.then(() => ...status.set('dragging'))
```

То есть достаточно передать провайдеру **любой** из этих пропов — и превращение
нажатия в перетаскивание встаёт в очередь за низкоприоритетной работой React на
доске, которая перерисовывается на каждый апдейт стора. Отпускание кнопки в этот
момент отменяет операцию: `canceled = !status.initialized`.

Хуже: промис обнуляется тем же коммитом, поэтому не доехавшая транзакция оставляет
вечно ждущий промис, и **каждое следующее** перетаскивание ждёт уже его.

Решение: подписка через `useDragDropMonitor` напрямую на `manager.monitor`, где
`trackRendering` нет, и провайдеру не передаётся ни одного `on*`.

## Дефект 4. SQLite терял одну из двух записей (и это не про перетаскивание)

**Существовал независимо от миграции и затрагивает любую параллельную запись, а не
только перетаскивание.**

Один дроп карточки пишет дважды одновременно (`Promise.all` в `onDropToColumn`):
свойство карточки и порядок карточек в виде. SQLite блокирует таблицу на запись, и
второе соединение не встаёт в очередь, а падает:

```
InsertBlock error occurred while updating existing block
  error="database table is locked: blocks"
API ERROR code=500 /api/v2/boards/.../blocks/<card>
```

Это `SQLITE_LOCKED`. `_busy_timeout`, который в строке подключения **есть**,
ретраит только `SQLITE_BUSY` — то есть не ретраил никто.

Дальше: webapp про неудачную запись молчит и оптимистичного обновления не делает,
поэтому доска продолжала показывать карточку в колонке, на которую сервер не
соглашался. С этого момента каждый следующий дроп в ту колонку для сервера —
пустая операция, рассылать нечего, и карточка не двигалась **никогда**.
Перезагрузка возвращала её туда, где её видел сервер.

Решение: `sqlDB.SetMaxOpenConns(1)` для SQLite — стандартное лекарство, и для
десктопа, где база это один файл на одной машине, бесплатное.

**Важно:** ставить **после** миграций. Миграционный движок держит одно соединение
и открывает второе, поэтому лимит в единицу вешает сервер на старте. Первая
попытка легла именно так.

**Что это значит шире:** любая пара параллельных записей на SQLite может потерять
одну. Десктопная сборка — это SQLite. Другие места, где webapp пишет несколько
блоков через `Promise.all`, до этой правки были подвержены тому же.

## Что осталось незакрытым

- **Webapp молча проглатывает неудачную запись.** Сервер вернул 500 — интерфейс
  показывает состояние, с которым сервер не согласен, и не говорит об этом.
  Ограничение соединения убрало одну причину, но глотание осталось.
- **Таблица, галерея и блоки контента** всё ещё на самодельной паре
  draggable + droppable (`useSortableBase`), а не на `useListSortable`. Нативного
  `draggable` там нет, так что дефект 1 их не касается, но переводить стоит.
- `TestPermissionsGetTeamTemplates` красный — и до всех этих правок тоже.
- E2E-спека добавляет около минуты к `cypress:ci`.

## Выводы

1. **Для плавающего дефекта воспроизведение важнее гипотезы.** Пять правок вслепую
   стоили дороже, чем один вечер на Cypress-спеку, которая потом нашла три дефекта
   за час.
2. **Воспроизведение должно быть честным.** Первая версия спеки дёргала указатель
   двумя рывками; после перехода на четырнадцать интерполированных шагов точка
   отказа сместилась с девятого перетаскивания на второе. Слишком добрый тест
   прячет дефект — и в итоге дефект 1 он не поймал вовсе.
3. **Не фильтровать чужие логи при отладке.** Решающая строка лежала в серверном
   выводе, который убирался грепом как шум.
4. **Молчащий отказ — сам по себе дефект.** Все четыре причины давали одинаковую
   картину именно потому, что каждая возвращалась молча: сенсор из guard clause,
   мутатор из проглоченной 500-ки, наш `dispatchDrop` из четырёх `return`.
5. **Проверять утверждения перед тем, как их делать.** `@dnd-kit/react` был назван
   экспериментальным по заголовкам старых issue; в README пакета — «Stable
   release».
